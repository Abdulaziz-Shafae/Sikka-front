# تجهيز الربط وصفحة الدفع

## الدمج

تمت مراجعة نسب الفروع قبل الدمج: شغل shefo وmohammed وnawaf داخل integration/four-updates-ready. نقل الباك إلى main كان fast-forward. تعارضات الفرونت في الملفات المشتركة حُلّت بالنسخة الأحدث مع الاحتفاظ بفلو الطعام وخريطة نواف والتقويم. فرع تجربة الخريطة المتحركة مستقل ولم يدخل الدمج.

## الصفحات الفعلية الجديدة

- `/connect`: دخول بحساب الباك الفعلي، قراءة زيارات الحساب، معاينة الجاهزية والاستحقاق، فتح الدفع.
- `/checkout/{visitId}`: السعر من preview، طلب الدفع من payment-order، إعادة استخدام الطلب المعلق، نموذج Moyasar.
- `/payment/return?order={orderId}&id={paymentId}`: لا يثق في status الموجود في رابط الرجوع؛ يستدعي confirm في الباك. النجاح يتطلب PAID وverifiedAt من رد الخادم.

الصفحة تعتمد فلو `src/main/resources/static/pay-test.html` الخاص بمحمد، مع عدم نقل تخزين كلمة المرور في sessionStorage. لا تجمع صفحة React بيانات البطاقة؛ نموذج Moyasar مسؤول عنها. لا يغير الفرونت مبلغ الطلب ولا يمنح الاستحقاق محليًا. الطلب المعلق يُحمّل من جديد قبل الدفع، ولا توجد إعادة محاولة تلقائية لإنشاء طلب أو خصم. إعادة تحميل الصفحة أو الرجوع من 3DS تتطلب تسجيل الدخول مجددًا لأن بيانات Basic Auth في ذاكرة الصفحة فقط. لا نحفظها في localStorage أو sessionStorage. الباك هو المسؤول عن ملكية الطلب والمبلغ والعملة والمرجع metadata.order_id ومنع استخدام الدفعة مرتين.

## إعداد الاتصال

انسخ القيم الموجودة في `.env.example` إلى بيئة التشغيل:

| المتغير | الاستخدام |
|---|---|
| `SIKKA_BACKEND_URL` | أصل خادم الباك فقط، مثل https://backend.example، على الخادم |
| `NEXT_PUBLIC_SIKKA_API_URL` | `/api/backend` لاستخدام بوابة من نفس النطاق |
| `NEXT_PUBLIC_MOYASAR_PUBLISHABLE_KEY` | مفتاح pk_test أو pk_live العام فقط |
| `NEXT_PUBLIC_SIKKA_DEMO_MODE` | يبقى true لواجهة التخطيط المحلية حتى استبدال أحداثها بالكامل |

المتغيرات NEXT_PUBLIC تُضبط وقت البناء. لا يُضاف أي secret key أو كلمة مرور إلى الفرونت. بوابة `app/api/backend/[...path]/route.ts` تقبل api/v1 فقط، لا تسمح بتحديد الخادم من الطلب، ولا تحفظ أو تسجل بيانات الدخول، وتمنع الطلبات ذات Origin مختلف. تستخدم HTTPS في الإنتاج، أو شبكة Railway الداخلية الموثوقة/localhost. البوابة تمرر Authorization؛ لا تعتمد على جلسة متصفح للباك.

عند النشر على Railway يستعمل railway.json بناء Next على Node وأمر تشغيل يحترم PORT ويستمع على 0.0.0.0. لم يتم نشر هذه المرحلة. المسار `/connect` هو فحص تشغيل الواجهة فقط وليس إثبات اتصال قاعدة البيانات.

## ما صار جاهزًا وما لا يزال متبقيًا

تم تجهيز عميل موحد يعالج 401 وأخطاء الخادم والمهلة، وتنزيل التقويم عبر العميل نفسه. تم إصلاح شاشة generating التي كانت تعود لنفسها؛ تحفظ الآن نتيجة المعاينة ثم تفتح plan. تم احترام isRateable القادم من الخادم وإضافة جسم requestKey لإكمال ActivitySession.

واجهة التخطيط الرئيسية ما زالت معاينة محلية صريحة. وجود API adapters لا يربط أحداث إنشاء الزيارة أو اختيارات الأعضاء أو سجل التنفيذ تلقائيًا. يلزم توصيل تلك الأحداث ودمج VisitRecord/ActivitySession مع الخطة، وإزالة تبديل هوية المعاينة قبل تفعيل الواجهة الرئيسية للإنتاج. لوحة الإدارة واللغة الإنجليزية الكاملة وGPS وواجهات البريد/واتساب الفعلية ليست مكتملة في هذه المرحلة. لا يعتبر /connect بديلًا عن إكمال كل هذه الشاشات.

## التحقق

`npm run typecheck` و`npm run check:flows` و`npm run check:integration` و`npm run build:railway` ثم `npm run check:production`.

فحص integration يستعمل HTTP mocks للتحقق من العناوين والأجسام والمبلغ والـmetadata وتأكيد الخادم وانتهاء المصادقة وحماية البوابة. لا يمثل خصمًا تجريبيًا من Moyasar أو اختبارًا على حساب Railway. اختبار بطاقة و3DS والدخول من المتصفح يحتاج باك شغالًا ومفتاح pk_test وإعدادات الإنتاج. لا تُعلن الصفحة دفعًا ناجحًا لمجرد نجاح الاختبارات.

نجح بناء Next على Node. فحص production يشغّل نسخة الإنتاج وباك محليًا وهميًا، ويتحقق من فتح الصفحات وتمرير طلب تأكيد الدفع بهويته وجسمه الصحيح ومنع Origin خارجي. هذا إثبات تشغيل محلي وHTTP فقط، وليس مراجعة بصرية أو نجاح 3DS فعلي.
